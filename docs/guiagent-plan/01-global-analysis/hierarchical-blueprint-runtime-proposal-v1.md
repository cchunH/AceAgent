# GUIAgent 分层蓝图运行机制提案与取舍评估 v1

## 文档元信息

- 状态：`active`
- 版本：`v1.0`
- 更新时间：`2026-04-14`
- 来源：基于当前代码现状与“页面指纹 + 图式流程 + 三层任务 + 渐进披露”思路的统一化提案
- 目标：作为下一阶段代码实现的设计约束与验收基线

## 1. 机制完整形态（目标定义）

本提案将系统定义为“可学习的图导航执行系统”，核心是把一次性推理转为可复用导航。

1. 页面级：`拓扑指纹`（Page Fingerprint）
- 通过离线复盘，将同一页面多次观测求交集，提炼稳定锚点（主锚点 + 辅锚点）。
- 用锚点的拓扑关系（节点、边、角色、区域）作为页面指纹。
- 在线阶段以 `OCR 文本 + 局部像素 + 拓扑匹配` 判断“是否到达目标页面”。

2. 流程级：`任务蓝图图谱`（Task Blueprint Graph）
- 复盘后把可复用流程保存为图结构：
  - 节点：规划层语义节点（子任务状态、目标状态）。
  - 边：执行层动作迁移（原子动作序列、约束、后验条件）。
- 下次执行时优先命中蓝图，按图导航而非全程从零推理。

3. 决策级：`大模型最小职责`
- 大模型负责“起始规划 + 偏差修正 + 不确定决策”。
- 常规动作由蓝图 + 页面指纹自动执行。
- 核心目标：减少 token 与认知负担，把模型从“动作生成器”降级为“导航监督者”。

## 2. 三层任务模型（规范化）

系统中的任务统一拆分为三层：

1. 复杂任务（L1）
- 面向用户完整意图，如“给某好友发送消息”。
- 产出：子任务工作流（L2 列表）。

2. 子任务（L2）
- 限定在特定 App/页面内的抽象操作，如“进入会话页”“发送文本消息”。
- 产出：原子任务链（L3）。

3. 原子任务/原子操作（L3）
- 设备可直接执行的动作：`Open_App/Tap/Type/Scroll/Back/Home/Send` 等。
- 必须绑定前置条件、页面指纹、后验校验。

补充约束：
- `intent_key` 需要分层命名（L1/L2/L3 对齐）。
- 蓝图存储应显式标注层级，避免将复杂语义压扁到单步 `Wait`。

## 3. 渐进披露策略（给模型的信息策略）

目标：让模型只在必要时看到必要信息，降低上下文负载。

1. L1 阶段（复杂任务）
- 只给复杂任务候选蓝图、子任务入口条件与失败策略。
- 不暴露大量原子动作细节。

2. L2 阶段（子任务执行）
- 披露对应页面指纹、可用子流程、局部约束。
- 按当前子任务提供可执行动作候选。

3. L3 阶段（原子执行）
- 仅披露当前动作所需局部信息：
  - 锚点候选
  - 拓扑投影
  - 前后置断言

## 4. 在线执行与离线学习闭环

1. 在线执行（运行时）
- 指令进入 -> L1 规划 -> 命中蓝图 -> 子任务导航 -> 原子执行 -> 断言校验 -> 偏差修正。

2. 离线复盘（事后）
- 聚合同页面执行轨迹 -> 生成稳定锚点交集 -> 更新拓扑指纹。
- 聚合成功路径 -> 生成/更新任务图边。
- 输出回灌补丁（delta patch），更新蓝图库。

3. 再利用（下一次）
- 新任务先做 L1/L2 命中检索。
- 命中后优先走蓝图导航，仅在偏差时请求模型重规划。

## 5. 与当前计划/实现的差异对照

## 5.1 已一致部分（可保留）

1. `state_engine` 已有去噪、静态骨架、拓扑匹配主链。
2. `blueprint_sync + delta patch + replay_gate` 已形成回灌闭环雏形。
3. `runtime_mode + v2_skip_legacy` 已提供独立演进通道。
4. `ActionRegistry/GuardPolicy/SessionRuntime` 模块化方向正确。

## 5.2 关键差距（需优先补齐）

1. 复杂任务语义仍会坍缩为 `Wait`
- 说明：L1 -> L2 -> L3 的层级结构未真正进入执行主链。
- 影响：纯 v2 无法稳定完成复杂任务。

2. 任务图谱与页面指纹尚未形成“强绑定导航”
- 说明：当前更偏“单步探针 + 后验回灌”，图导航能力弱。
- 影响：可复用收益不足，复杂场景仍依赖临时推理。

3. 渐进披露机制未成体系
- 说明：上下文压缩已有，但分层披露策略还未产品化落地。
- 影响：模型上下文利用效率不稳定。

4. 验收门禁存在“假成功风险”
- 说明：此前出现过 `task_end` 与 flow audit 口径不一致，虽已修正一部分，仍需完善“语义成功”判定。
- 影响：实测数据可信度受损。

## 6. 取舍评判（建议）

结论：应采用“你的思路为主线，现有实现为骨架”的渐进升级路线，不建议另起体系。

1. 保留现有模块化骨架
- 原因：事件、策略、回灌、状态面已具备工程基础，重建成本高。

2. 重构任务语义层（优先）
- 原因：当前最大瓶颈不是执行器，而是 L1/L2/L3 未贯通。

3. 推迟非核心扩展
- 群智联邦分发继续后置，不进入当前里程碑。

## 7. 下一阶段实施建议（按优先级）

1. P0：语义正确性与日志可信度
- 把 `Wait` 退化统一视为失败/交接，不得记成功。
- flow_audit 强制校验 `task_end` 与语义目标一致。

2. P1：三层任务主链落地
- 新增 `task_planner`（L1->L2）与 `subtask_planner`（L2->L3）。
- 执行器按 L3 原子动作执行，失败回到上层重规划。

3. P2：页面指纹强绑定导航
- 子任务节点必须挂接页面指纹与通过条件。
- 每次执行更新节点-边可信度，形成可学习图。

4. P3：渐进披露策略化
- 按层级动态下发上下文（L1/L2/L3）。
- 结合 `ContextCompactor` 形成分层记忆窗口。

## 8. 验收标准（建议新增）

1. 复杂任务成功率
- L1 任务不应再以单步 `Wait` 成功结束。

2. 蓝图复用收益
- 命中蓝图任务的平均步骤数、时延、token 消耗显著下降。

3. 页面识别稳定性
- 同一页面多次进入的拓扑匹配稳定（置信度方差受控）。

4. 语义一致性
- `task_end`、flow_audit、validation_gate 对同一任务给出一致结论。

1. 群智联邦分发（后置）。
2. 大规模跨端协同训练（后置）。
3. 重写状态面底层（不做，维持兼容增量）。

### 10.2 建议采用的主路线

1. 以你提出的“图导航 + 分层披露”作为目标架构。
2. 以现有 `guiagent_v2` 模块作为承载骨架做增量改造。
3. 每轮迭代先保证“能完整跑通复杂任务”，再做性能与泛化优化。
