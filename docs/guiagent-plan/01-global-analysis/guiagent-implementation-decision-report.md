# GUIAgent 实施路径决策报告（现有项目迭代 vs 新开项目）

## 1. 决策问题

目标：实现 GUIAgent 蓝图，应该在现有 Uni-Mind 上继续迭代，还是新开项目重做？

## 2. 方案对比

### 方案 A：在现有 Uni-Mind 直接迭代

优点：
- 可复用感知/执行/日志/学习基础，启动成本低。
- 研发反馈快，最容易快速做 PoC。

缺点：
- `orchestrator.py` 复杂度高，直接叠加新架构会进一步恶化。
- 旧协议（字符串解析）与新契约（schema）冲突明显。

适用条件：
- 小团队、短周期、先验证关键技术可行性。

### 方案 B：新开项目重构

优点：
- 可以从第一天按“蓝图契约 + 编译执行”设计，不背历史包袱。
- 架构边界清晰，利于后续群智网络服务化。

缺点：
- 重复建设成本高，短期价值交付慢。
- 容易失去现有系统的稳定能力和经验积累。

适用条件：
- 资源充足、追求中长期平台化、可接受 2~3 个月低产出窗口。

### 方案 C：推荐方案（混合：同仓并行孵化）

定义：
- 保留 Uni-Mind 主链可运行。
- 在同仓新增 `guiagent_v2` 子系统，逐步替换旧执行内核（Strangler 模式）。

优点：
- 既复用现有能力，又避免在旧编排上“硬补丁”。
- 可分阶段上线，风险可控。

缺点：
- 过渡期会有双栈维护成本。

## 3. 推荐结论

推荐 **方案 C（同仓并行孵化）**，不建议立即纯重写。

理由：
1. 现有系统有可观复用价值（感知、动作执行、学习入口、日志）。
2. GUIAgent 的核心新增是“契约与运行时”而非“设备操作底座”。
3. 通过并行孵化可以快速验证关键风险点，再决定是否独立拆仓。

## 4. 建议实施形态

建议在当前仓新增目录（示意）：

```text
guiagent_v2/
  intent_contract/
  state_engine/
  action_engine/
  blueprint_hub/
  evolution_patch/
  brain_adapter/
```

衔接方式：
- 短期：`brain_adapter` 先复用现有 Planner/Executor。
- 中期：将 `orchestrator` 的执行分支切到 `action_engine`。
- 长期：将群智网络能力外置为服务（可另仓）。

## 5. 何时考虑拆分新项目

满足以下任一条件可考虑拆分：
1. 需要独立部署 `Swarm Hub`（多租户、合规、安全审计）。
2. `guiagent_v2` 代码量/依赖规模超过现仓维护边界。
3. 团队分工转向平台化产品团队，需要独立版本节奏。

## 6. 决策门槛（Go/No-Go）

### Go（继续推进）
- 单机闭环 PoC 达到：成功率 > 90%，S2 接管率下降明显，执行时延显著下降。

### No-Go（暂停或转向）
- 状态面锚点匹配在核心场景持续不稳，无法形成可复用蓝图。
- 契约化改造导致主链不稳定且无法隔离影响面。
