# 系统设计权衡分析（Trade-off Analysis）

本文聚焦“为什么这么设计、代价是什么、何时应调整”。

## 1. 可靠性 vs 效率

### 当前设计
- 专家轨强调稳健：逐步规划、逐步验证（`orchestrator.py` + `expert_track_agents.py`）。
- 快轨强调效率：批量动作 + 快速验证（`fast_track_agents.py`）。

### 优点
- 双轨理论上可同时覆盖复杂任务与简单任务。

### 代价
- 双轨协议与调度逻辑增加系统复杂度。
- 当前 `USE_DUAL_TRACK=False`，快轨收益尚未在默认路径兑现。

### 何时调整
- 若线上任务以“短链路、高重复”居多，优先推进快轨参数化与验证治理。
- 若任务长链且变化大，优先增强专家轨可解释性与容错。

---

## 2. 可解释性 vs 生成灵活性

### 当前设计
- Agent 输出采用“半结构化文本 + JSON”混合协议。

### 优点
- Prompt 灵活，便于快速迭代 Agent 行为。

### 代价
- 字符串切分解析脆弱，失败路径复杂。

### 何时调整
- 当解析失败占比上升或排障成本过高时，转向 schema-first 协议。

---

## 3. 通用能力 vs 专项优化

### 当前设计
- Perceptor 采用通用 OCR + icon 检测 + caption，覆盖面广。
- ActionExecutor 支持技能编排，具专项效率潜力。

### 优点
- 可迁移到多种 App 场景。

### 代价
- 感知链成本高，且对噪声较敏感。

### 何时调整
- 针对高频场景可引入专项轻量感知器，降低时延。

---

## 4. 简单实现 vs 并发一致性

### 当前设计
- 通过线程异步执行低依赖 Notetaker，提升吞吐。

### 优点
- 主循环可减少阻塞。

### 代价
- 线程生命周期与状态一致性治理不足。

### 何时调整
- 当出现“笔记晚到/覆盖异常”时，引入线程池与任务收尾屏障。

---

## 5. 快速落地 vs 长期治理

### 当前设计
- 代码可快速扩展功能，但治理设施（指标、错误码、策略管理）偏薄。

### 优点
- 研发节奏快，探索成本低。

### 代价
- 长期维护压力增大，质量上限受限。

### 何时调整
- 从单人实验转向团队协作或持续运行时，优先补治理层。

---

## 6. 关键决策建议（按阶段）

### 阶段A：先补治理
- 参数化策略开关（快轨、交互式暂停、日志级别）。
- 统一错误分类与指标输出。
- 清理密钥与配置安全问题。

### 阶段B：再做架构重构
- 拆分 orchestrator 状态机。
- Agent 协议 schema 化。
- 学习机制加质量门控。
